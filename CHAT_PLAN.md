# План: чат, совместная работа и комментарии в блокноте

Статус: **черновик, ждёт решений** (раздел «Вопросы до старта»). Код не начат.

Цель: работать вместе над документом или целой папкой блокнота — совместная правка в реальном времени, комментарии к строкам и блокам, чаты внутри документов (`@чат` / `@chat`), лента всех обсуждений, уведомления. Связь между копиями приложения — через свой бэк-сервис (сокеты, своя БД). Без учётных записей: устройство узнаётся по своему ключу, имя каждый задаёт себе сам.

---

## 1. Архитектура

```
Qvarch ─┬─ renderer: CodeMirror + y-codemirror (текст, курсоры), панели комментариев / чата, лента
        └─ main/collab: CollabClient (одно wss-соединение), локальный кэш Y.Doc (SQLite), зеркало .md на диск
                 ⇅  wss (TLS) — синхронизация Yjs + присутствие + RPC + события обсуждений
collab-server (Node, ws) ─ PostgreSQL: устройства, пространства, права, документы, обновления, снимки, файлы, обсуждения
```

- **Пространство (workspace)** — общая папка (частный случай — один документ): дерево файлов + документы.
- **Совместный текст — Yjs (CRDT)**: у CodeMirror 6 есть готовая привязка `y-codemirror.next` — общий текст, курсоры других, своя отмена у каждого. Свой алгоритм слияния не пишем.
- **Y.Doc документа — источник правды**, файл `.md` на диске — его зеркало (пишет приложение): поиск, пакеты, «Выполнить всё», инструменты ИИ работают как раньше.
- **Дерево папки — тоже CRDT** (`Y.Map` `docId → { путь, имя, удалён }`): создание / переименование / перенос сливаются; документ узнаётся по `docId`, не по пути.
- **Сервер**: хранит обновления, ужимает их в снимки, раздаёт изменения онлайн-участникам, досылает пропущенное по векторам состояния; держит в памяти только открытые документы.
- **Клиент**: одно соединение на всё приложение (в main), комнаты и документы мультиплексируются; сжатие, пачки, история страницами — минимальная нагрузка.

## 2. Личность без авторизации

- **Пара ключей на установку** (Ed25519 — подпись, X25519 — шифрование; есть в `node:crypto`), создаётся **один раз** при первом запуске и хранится постоянно. Идентификатор устройства — отпечаток публичного ключа.
  - Голый UUID не годится: кто его узнал — выдаст себя за другого; новый UUID на каждый запуск — человек «новый» после перезапуска.
- Приватный ключ — в `safeStorage` (DPAPI). Экспорт / импорт ключа файлом с паролем — перенос на другой компьютер.
- Сервер при подключении проверяет **подпись случайного вызова** — без паролей и учёток, но подделать чужое устройство нельзя.
- **Имя** — «Настройки → Совместная работа». Рядом всегда короткий отпечаток (два «Ивана» различимы; имя ничего не гарантирует).
- **Доступ к серверу**: общий код сервера (вводится один раз) или разрешённые подсети — иначе подключится любой во внутренней сети.

---

## 3. Права

- Роли в пространстве: **владелец, редактор, комментатор, читатель**.
- Приглашение — по коду или из списка устройств, которые видел сервер (имя + отпечаток).
- Удалить пространство / чат «у всех», менять роли — владелец. Участник может «Покинуть».

---

## 4. Шифрование

- **Канал** — TLS (`wss://`), сертификат внутренний или самоподписанный с проверкой отпечатка из настроек.
- **Хранение — выбор (см. вопросы):**
  - **А (рекомендация для начала): TLS + шифрование в БД ключом сервера.** Сервер сам сливает и ужимает обновления — просто и быстро. Минус: администратор сервера технически может прочитать.
  - **Б: сквозное шифрование** (ключ пространства / комнаты AES-256-GCM, разослан участникам, обёрнутый их X25519). Сервер хранит только шифротекст. Минус: ужимать в снимки должны клиенты, удаление участника — ротация ключа и перешифровка; примерно вдвое дороже.
  - Протокол закладываем так, чтобы А → Б можно было перейти позже.
- **Локальный кэш** (Y.Doc, обсуждения) — SQLite в main, ключ — `safeStorage`.
- Сообщения чатов и комментарии **не пишутся в `.md`** (иначе попадут в пакеты, поиск, git и будут читаемы с диска).

---

## 5. Совместная правка: нюансы

1. **Правки с диска** (другой редактор, git, распаковка пакета): отслеживание хранилища замечает → разница файла с Y.Doc применяется как обычные правки. Свою запись зеркала узнаём по хешу — без петли.
2. **Блоки-компоненты** сейчас заменяют свой текст целиком → двое, правящие разные ячейки таблицы, затрут друг друга. Решение: `replaceComponent` применяет **минимальную разницу текста**; правки разных строк / ячеек сливаются, одна ячейка — «последний побеждает».
3. **Результаты запусков и переменные — локальные** (у каждого свои подключения, токены, данные; `.runs` не синхронизируются). По желанию — «Опубликовать результат»: снимок уходит в обсуждение.
4. **Секреты в тексте** — главный риск: текст видят все. Проверка при открытии доступа и при правке (токены, cookie, пароли) с предупреждением; подталкивать к переменным из локальных настроек HTTP / подключений (`{{token}}` в тексте, значение у каждого своё).
5. **Отмена** — `Y.UndoManager`: Ctrl+Z откатывает только свои правки. История CodeMirror для общих документов выключается.
6. **Без сети**: правки копятся и сливаются при подключении; статус «синхронизировано» / «N изменений ждут сети».
7. **Медиа** (картинки, аудио, вложения) — файлы по хешу содержимого, загрузка по требованию, ограничение размера.
8. **Удаление**: удалён у всех, а кто-то правил без сети → у него появляется **восстановленная копия** с пометкой (текст молча не теряется). Удалённое — в корзину пространства на N дней.
9. **Дерево и текст одновременно**: переименование / перенос правке не мешают (`docId`); одинаковые имена новых файлов → « (2)».
10. **Поделиться / перестать**: при открытии доступа Y.Doc строится из текущего файла; при выходе у ушедшего остаётся обычная локальная копия.
11. **Присутствие**: цвет и имя участника, его курсор и выделение, в шапке — кто сейчас в документе.
12. **История версий**: снимки по времени и автору, сравнение, «Восстановить» (тоже правка — сливается со свежими изменениями).
13. **Копирование блока чата** (недавно появились «Дублировать» и действия над несколькими блоками): копия блока с тем же `room=` не должна тихо стать второй ссылкой на ту же комнату — при дублировании / вставке спрашивать «новая комната» или «ссылка на этот чат»; перенос (вырезать-вставить) — та же комната.

## 6. Комментарии к строке и блоку

- **Привязка к позиции в CRDT** (`Y.RelativePosition` начала и конца), не к номеру строки — комментарий едет с текстом. Текст удалён → комментарий «текст удалён», остаётся в списке.
- В редакторе: метка на полях, подсветка диапазона, обсуждение во всплывающем окне (`<Popover>`), панель «Комментарии документа» (открытые / решённые, фильтры).
- Комментарий к строке, фрагменту или к блоку целиком (таблица, SQL).
- Ответы, реакции, упоминание `@имя`, «Решено» / «Открыть снова».
- Роль «комментатор» — видит и комментирует, текст не правит.

---

## 7. Чат: одна модель обсуждений

Чат и комментарии — один механизм, разная привязка:

| Привязка | Что это |
|---|---|
| `range` (позиция в CRDT) | комментарий к строке / фрагменту |
| `block` (` ```chat room=<id> `) | чат внутри документа — каждый новый блок открывает новую комнату |
| `document` | общее обсуждение документа (панель сбоку) |
| `workspace` | чат пространства (папки) |

- **Общее для всех**: сообщения (markdown), правки и удаления, реакции, упоминания, «печатает…», присутствие, прочитано (по `seq`), очередь отправки без сети, досылка пропущенного.
- **Порядок**: сервер выдаёт сквозной `seq` в комнате; клиент при подключении присылает последний `seq` по каждой комнате.
- **Групповые чаты** — любая комната с N > 2 участниками; добавление из списка устройств или по коду.
- **Блок `@чат` в общем документе** видят все участники документа. **Изолированный чат** — свои участники, вне общего документа.

### Что можно отправить (поле ввода — тот же редактор с «@»)

- **SQL с данными** — запрос + снимок результата (лимит строк / размера, «снимок от …»).
- **HTTP** — запрос + ответ. **Тесты / Playwright** — сценарий + результат. **Таблица** — её значение. **Заметка / файл** — вложение.
- Снимки — **реестр адаптеров по типу блока** (`chatSnapshot` в spec блока), без `if` по типам.
- **Обязательно**: вычистить секреты (токены, cookie, `Authorization`, пароли подключений, переменные HTTP) и показать отправителю, что вырезано.
- **Чужие блоки сами не выполняются**: «Выполнить у себя» — с предупреждением; подключение к БД — своё (по совпадению имени).

### Удаление

- Убрать блок из текста ≠ удалить чат (чат остаётся в ленте).
- «Удалить чат у всех» — владелец; надгробие уходит всем, клиенты стирают комнату, сообщения и блок. Удалить у тех, кто скопировал текст, нельзя — сказать об этом честно.

## 8. Документы в папке «Чаты» (для изолированного чата и «поделиться снимком»)

Если чат создан не в общем пространстве:

- У собеседника появляется документ `Чаты/<Название>.md` с блоком чата.
- **Поделиться документом** (вместо полной совместной правки) — снимок документа автора. Документ получателя делится на зоны:

  ```md
  <!-- qa:shared from=<author> room=<id> v=3 -->
  …общая часть (обновляется у всех по кнопке автора)…
  <!-- qa:shared-end -->
  …свои записи получателя (если были до снимка — оказываются здесь, внизу)…
  ```

  Обновление заменяет только общую зону; правки внутри неё перезапишутся (предупреждение, «Отделить копию»). Медиа уходят вложениями, секреты вычищаются.
- Коллизии имён — « (2)»; связь держится на `room=`, переименование / перенос не рвут её.

---

## 9. Лента «Все обсуждения»

- `Чаты/Все чаты.md` создаётся при первом обсуждении и содержит **один блок `@chatfeed`** — рисуется из локальной БД (файл не переписывается на каждое сообщение: ни отслеживания, ни поиска, ни шума в git).
- Чаты, новые комментарии, упоминания — по всем пространствам и документам; группы по документу и названию; новые сверху; счётчики непрочитанного.
- Ответить прямо из ленты; «Открыть документ» — к блоку / строке с прокруткой.

## 10. Уведомления

- Уведомление Windows **без кражи фокуса**; клик — документ и прокрутка к блоку / строке (`qa://collab/<doc>/<anchor>`).
- В приложении: значок на разделе «Блокнот», счётчик на блоке и в ленте, точка на island.
- Без звука для чата / пространства, «только упоминания», «не беспокоить» вне рабочего графика.
- Не показывать, если тот же документ открыт и окно активно.

## 11. Сервер и БД

- **Таблицы**: `devices`, `workspaces`, `members(role)`, `docs(id, workspace, path, deleted)`, `doc_updates` (только дописываются), `doc_snapshots`, `blobs`, `threads(anchor)`, `messages`, `reactions`, `read_state`.
- **Протокол** (один сокет): синхронизация Yjs (шаги 1 / 2, обновления), присутствие, RPC (пространство, права, обсуждения), события обсуждений.
- **Нагрузка**: бинарные обновления Yjs со сжатием; присутствие — не чаще нескольких раз в секунду; простаивающие документы выгружаются; ужатие в снимок каждые N обновлений; ограничение частоты запросов.
- **Версии протокола**: клиент сообщает свою, сервер отказывает несовместимым с понятным сообщением.

## 13. Этапы

1. **Сервер и личность** — ключи, имя, подключение по подписи, пространства и роли, «Поделиться документом».
2. **Совместная правка документа** — Y.Doc ⇄ CodeMirror, курсоры, своя отмена, зеркало `.md` и правки с диска, минимальная разница для блоков, работа без сети.
3. **Общая папка** — дерево как CRDT, медиа, корзина, восстановленные копии.
4. **Комментарии** к строкам и блокам — обсуждения, решено / открыто, упоминания, уведомления с переходом к строке.
5. **Чат и лента** — блок `@chat`, обсуждение документа и пространства, снимки SQL / HTTP / тестов, изолированные чаты и папка «Чаты», лента «Все обсуждения».
6. **История версий**; при необходимости — переход на сквозное шифрование (вариант Б).

## 14. Вопросы до старта

1. **Шифрование**: вариант А (TLS + шифрование в БД; сервер может прочитать) или сразу Б (сквозное, дороже)?
2. **Сервер**: какая машина, отдельная PostgreSQL или общая, сертификат (внутренний CA / самоподписанный с отпечатком), код доступа к серверу или подсети?
3. **Роли**: хватит четырёх на пространство или нужны права на отдельные документы внутри папки?
4. **Новые участники**: видят всю историю обсуждений или с момента добавления?
5. **Результаты запусков**: только локально или «Опубликовать результат» уже на этапе 2?
6. **Изолированный чат вне пространства**: нужен в первой версии или достаточно чатов внутри общих документов?
7. **Библиотеки**: `yjs`, `y-codemirror.next`, `y-protocols`; на сервере — `ws`, драйвер PostgreSQL. Добавляем?
