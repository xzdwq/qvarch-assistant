# Автоматизация в блокноте: оболочка, документы-функции, панель выполнения

Дата: 2026-11-06. Статус: на утверждении.

## Зачем

Заметка блокнота становится сценарием автоматизации, который пользователь пишет как код в проекте:
- шаги по порядку: команды PowerShell / cmd / bash (позже — на сервере по SSH), HTTP, Playwright, чтение файлов;
- условия в JS/TS-блоках;
- вызов других документов как функций, с параметрами и результатом.

Пример. Заметка «Проверка диска» выполняет `Get-PSDrive C` и берёт из вывода свободное место. JS-блок сравнивает его с порогом. Если места мало — вызывается документ «Очистка диска» с параметром `порог`. Он чистит кэш npm, pnpm, Temp, Docker: какие пункты выполнять, пользователь отмечает галочками. Результат пишется в чат, или ИИ получает задачу разобраться.

Запускает пользователь сам: кнопкой «Выполнить всё» или существующим cron-блоком. Всё, что идёт в фоне (cron в свёрнутом приложении, вызванные документы), видно в одной панели, и оттуда же останавливается.

## Цели

1. Блок оболочки: PowerShell, cmd, bash. Вывод — значение заметки, построчно, с фильтром по регулярке.
2. Галочка у каждого запускаемого блока и цикла: участвует ли он в «Выполнить всё».
3. Документ как функция:
   - объявленные параметры (видны как сигнатура);
   - результат (аналог `return`);
   - вызов из компонента с выбором документа мышкой или поиском;
   - вызов из кода по имени компонента;
   - синхронно и асинхронно.
4. Фоновые прогоны:
   - вызов не трогает сохранённые результаты вызванного документа;
   - открытый документ показывает, что в нём выполняется сейчас.
5. Панель «Выполнение» (строка состояния в футере, по клику открывается панель, как терминал):
   - дерево прогонов: цепочка вызовов, текущий блок, логи;
   - остановка одного прогона или всех.
6. Шаги «в чат» и «спросить ИИ». ИИ через свои MCP-инструменты сам выбирает и запускает документ, проверяет что-то или пишет логику.
7. Чтение файлов с диска (txt, csv, xlsx, json) в значение.
8. SSH: сохранённые сессии, как в MobaXterm. Блок оболочки на удалённой машине, вкладка терминала по сессии.

## Не цели

- Свой планировщик: расписание — существующий cron-блок.
- Слежение за файлами и событиями ОС как триггер: опрос по cron покрывает это сейчас.
- Визуальный конструктор потоков (рисование стрелок): поток — это текст заметки, панель его только показывает.
- Разбор вывода «умными» парсерами под конкретные программы: только строки, регулярки и код пользователя.

## Чего нельзя допустить (провал, даже если работает)

- Вызов документа портит сохранённые результаты или вид этого документа, а параллельные вызовы с разными параметрами перетирают друг друга.
- Фоновый прогон невидим: его нельзя найти и остановить без поиска нужного документа.
- Блок оболочки запускает что-то, что переживает «Стоп» (дочерние процессы остаются висеть).
- Большой вывод (гигабайты строк) копится в памяти или в значении целиком.
- Секреты (пароли SSH, токены из параметров) попадают в логи, отчёты, значения или ответы ИИ.
- Частные случаи по типам блоков цепочками `if`; демо-данные и названия проектов в коде.

## Ограничения (из правил проекта)

- Наборы значений — `as const` в модуле констант контекста; реестры вместо `if/else` по типу.
- Чистая логика — в `src/shared` или чистых модулях `@nb/domain` / `@nb/engine` (видна тестам), и покрыта vitest в той же задаче.
- Новый блок — одна папка `blocks/<kind>/` + строки в трёх реестрах (`blocks/specs.ts`, `engine/runners.ts`, `ui/blockViews.ts`).
- Процессы — только через `ProcessSupervisor`.
- Всплывающие меню — `usePopover` / `<Popover>`; выбор с подсказками — `SuggestInput`.
- Блок заметки: `contain: inline-size; min-width: 0`; широкое содержимое прокручивается внутри.
- Файл ≤ ~400 строк, комментарии короткие на английском.

## Устройство по этапам

Этапы делаются по порядку, каждый — отдельной поставкой со сборкой.

### Этап 1. Блок оболочки и галочка «в Выполнить всё»

**Запись в Markdown.**

```` 
```powershell run name=disk timeout=60
Get-PSDrive C | Select-Object Free
```
````

- Языки — отдельный набор `SHELL_LANGS` (`powershell`, `pwsh`, `ps1`, `cmd`, `bat`, `bash`, `sh`) рядом с `CODE_LANGS` в `domain/blockInfo.ts`, не внутри `CODE_LANGS`.
- Как запускать каждую оболочку — таблица в `shared` (язык → оболочка, аргументы, как передать скрипт, кодировка вывода):
  - **PowerShell:** `pwsh.exe`, если установлен, иначе `powershell.exe`. Аргументы `-NoProfile -NonInteractive -EncodedCommand <base64 utf16le>` (без проблем с кавычками и политикой выполнения), в начале скрипта — UTF-8 для вывода.
  - **cmd:** временный `.cmd` с `chcp 65001`.
  - **bash:** найденный `bash.exe` (Git Bash, WSL) с `-lc`. Нет оболочки — понятная ошибка «не найдено: …», не падение.
- Подстановка `{{x}}` в тексте скрипта — как в HTTP-блоке (`interpolate`), до отправки в main. Значения передаются ещё и переменными окружения `QA_<имя>` — для безопасной передачи без экранирования.
- Настройки: `cwd=` (по умолчанию домашняя папка), `timeout=` (существующий), `soft` (существующий), `match=/регулярка/флаги` — фильтр строк.

**Выполнение.**
- Main, новый воркер `main/runner/shellWorker.ts` под `ProcessSupervisor` (тайм-аут, окно-владелец, временная папка).
- Окружение — `windowsShellEnv()` (свежие переменные из реестра).
- «Стоп» и тайм-аут убивают всё дерево процессов (на Windows — `taskkill /T /F` по pid), иначе остаются дочерние.
- stdout и stderr идут потоком по существующему каналу `emit` (живой вывод в блоке).

**Значение блока** (`name=`):

```
{ exitCode, ok, stdout, stderr, lines: string[], matches?: string[][], truncated?: boolean, ms }
```

- `lines` — строки stdout.
- При `match=` в значение попадают только совпавшие строки и группы регулярки (`matches`), полный вывод не копится.
- Предел хранения — последние ~2 МБ на поток, флаг `truncated`. Журнал прогона (этап 3) тоже хранит только хвост в памяти (кольцевой буфер), не весь вывод; на диск поток не пишется.
- Ненулевой код выхода — ошибка блока (кроме `soft`).
- Регулярка компилируется и выполняется с ограничением времени — переиспользовать подход `watchScanner` (`compileWatch`).

**Доверие: кто может запустить скрипт оболочки** (решение пользователя: вариант «свои — да, чужие и изменённые ИИ — после одобрения» + настройка блока).
- Скрипт, который пользователь сам написал или изменил в редакторе своей заметки, разрешён сразу.
- Скрипт требует одобрения, если текст блока последним изменил не пользователь:
  - пришёл из общей папки или пространства другого человека;
  - изменён ИИ (инструменты записи заметок);
  - изменён синхронизацией.

  Одобрение привязано к отпечатку текста блока (скрипт + строка ограды). Любое чужое изменение снимает его.
- Настройка блока `ask=`:
  - `auto` — по умолчанию, правило выше;
  - `always` — спрашивать перед каждым запуском;
  - `never` — разрешить всегда без вопросов.

  Настройка — часть отпечатка: `never`, вписанный другим человеком или ИИ, действует только после одобрения пользователем.
- Вопрос «Разрешить запуск?» показывает скрипт целиком и откуда он (кто изменил). Если окна блока нет на экране (cron в свёрнутом приложении, вызов, ИИ), вопрос появляется в строке состояния и панели «Выполнение» (этап 3; до него — уведомлением окна). Прогон ждёт ответа. Без ответа за 10 минут — ошибка «не одобрено».
- Хранение одобрений — в main (`data/`), по отпечатку. Проверка — в одной точке, через которую проходит любой запуск оболочки (вручную, «Выполнить всё», cron, ИИ, вызов документа), а не в каждом пути отдельно.
- Чистая часть (отпечаток, решение «разрешить / спросить / отказать» по источнику изменения и настройке) — с тестами.

**Галочка «в Выполнить всё».**
- Флаг `skip` в строке ограды (`FLAGS`, `infoMd`) и в комментарии цикла (`parseLoopInfo` / `loopInfoMd`).
- Флаг действует при любом пакетном прогоне: «Выполнить всё», каждый проход цикла (в том числе при ручном запуске всего цикла), прогон вызванного документа. Ручной запуск самого блока его игнорирует. Значит, отбор — в общем построении списка пакетного прогона, с параметром «ручной запуск одного блока» вне его.
- Галочка — в общем `ui/RunHead.vue`, через `useFenceSource().patchInfo`, как «не останавливать» у Playwright. Отмечено — участвует.
- Пропущенный блок в отчёте и в `runs` — состояние «пропущен».

### Этап 2. Документ как функция

**Параметры — блок `params`** (новый вид блока). В Markdown:

```` 
```params
- name: порог
  type: number
  default: 10
  description: Свободное место, ГБ, ниже которого чистить
- name: сервер
  type: string
  required: true
```
````

- Рисуется как сигнатура функции: `Очистка диска(порог: number = 10, сервер: string)`, под ней строки параметров с описаниями. Правка — формой (строка = параметр).
- Типы — набор `as const`: `string`, `number`, `boolean`, `json`, `secret`.
- **Секреты маскируются по значению, как в CI** (решение пользователя). Каждое вхождение значения известного секрета заменяется на `•••` во всём, что выходит наружу:
  - потоки `emit` (вывод оболочки, `console` кода);
  - опубликованные значения и `result`;
  - журнал прогона и панель;
  - отчёты;
  - синхронизация результатов общих заметок (`sharedRuns`);
  - всё, что видит ИИ.

  Известные секреты: аргументы типа `secret` всех прогонов в дереве вызова, позже пароли сессий SSH. Фильтр — один чистый модуль (набор секретов → функция маскировки строк и вложенных значений, включая части секрета в base64 и URL-кодировке), подключённый в каждом пути вывода. Тесты на каждый вид кодирования. Внутри выполнения (в запросе HTTP, в процессе оболочки) секрет настоящий.
- Модель и проверка аргументов — чистый модуль (разбор, слияние с умолчаниями, приведение типов, ошибки «нет обязательного параметра», «не число») с тестами.
- Во время прогона аргументы — значение `args` (зарезервированное имя): `{{args.порог}}` в подстановках, `args.порог` в коде.
- Ручное «Выполнить всё» у документа с обязательными параметрами без умолчаний спрашивает их формой перед стартом.

**Результат — блок `result`** (новый вид блока, аналог `return`).
- Тело — JSON с подстановками, вычисляется, когда до него доходит очередь: `{ "free": "{{disk.matches.0.1}}" }`.
- Публикует значение `result`.
- Вызов возвращает `result`, если он есть, иначе объект всех значений прогона.

**Вызов — блок `call`** (новый вид блока):

```` 
```call note="Обслуживание/Очистка диска" name=cleanup
порог: "{{limit}}"
```
````

- Компонент: выбор документа — `SuggestInput` с поиском по дереву блокнота (путь, название) и кнопка «открыть». Под ним — форма параметров, построенная из блока `params` вызываемого документа. Тело блока — значения аргументов с подстановками.
- Ссылка хранится путём; при переименовании или переносе заметки путь обновляется так же, как обновляются вики-ссылки (найти и переиспользовать существующий механизм переименования).
- Без флагов блок выполняется на своём месте в «Выполнить всё», ждёт окончания и публикует результат под `name`.
- `async` — запустить и идти дальше. Значение — описатель прогона `{ runId }`; дождаться можно позже из кода.
- `lib` (существующий смысл «объявление, не выполнять») — блок становится импортом. Он не выполняется сам, а в коде появляется функция с его именем: `const r = await cleanup({ порог: 5 })`. Без `await` — асинхронно, `Promise.all` — параллельно.
- Канал «код → вызов документа → ответ» — по образцу круга прохода цикла (`loopWorker` ↔ `onLoopPass` ↔ `runLoopPass`): воркер кода шлёт запрос, main передаёт его окну, окно выполняет и отвечает. Песочница кода получает функции только для `call lib` блоков своей заметки — общей функции «вызвать что угодно по строке» нет.

**Фоновые прогоны.**
- Новое понятие движка — прогон (`Run`): id, путь документа, аргументы, родительский прогон, триггер (`by: 'note'`, кто вызвал), своё изолированное окружение значений (в памяти, не пишет в `vault/.runs`), состояние блоков, журнал.
- Ручной запуск и cron работают как сейчас (пишут сохранённые результаты), но тоже регистрируются как прогоны: их видно в панели и можно остановить.
- Вызванный документ всегда идёт в изолированном окружении: параллельные вызовы с разными параметрами не мешают друг другу и сохранённым результатам.
- Реестр прогонов (`engine/runRegistry.ts`): дерево активных и недавних (последние ~50 завершённых) прогонов. Остановка прогона останавливает его поддерево. Чистая часть (дерево, состояния, переходы, обрезка журнала) — с тестами.
- Рекурсия разрешена, глубина вызовов ограничена (16). Превышение — ошибка с цепочкой вызовов.
- Время жизни асинхронного вызова — как промис в JS:
  - асинхронный вызов остаётся в дереве своего родителя и продолжает работать после того, как родитель закончил;
  - «Стоп» родителя (и всего поддерева) останавливает и его;
  - синхронный вызов возвращает результат, когда выполнились блоки вызванного документа, и не ждёт асинхронных вызовов внутри него.

  Корневой прогон в дереве считается законченным, когда закончились все его потомки.
- Cron у документа с обязательными параметрами без значений по умолчанию — прогон падает с ошибкой «нет обязательного параметра …». Аргументы в задаче cron не хранятся (умолчания в `params` покрывают расписание).
- ИИ получает MCP-инструмент «вызвать документ»: путь, аргументы по `params`, ответ — результат. Прогон изолирован, как вызов из другого документа. Существующий запуск ИИ (`runAll` с `by: 'ai'`) остаётся как есть.
- Открытый документ с активным фоновым прогоном показывает полосу «Выполняется в фоне — вызвано из …». Если прогонов несколько — выбор. Блоки показывают живые состояния выбранного прогона вместо сохранённых результатов; переключатель «сохранённые результаты / прогон».

### Этап 3. Панель «Выполнение»

- Строка состояния в футере окна: «▶ N выполняется». Пусто — элемента нет; последняя ошибка видна несколько секунд. Клик — панель.
- Панель снизу, как терминал (переиспользовать подход `TermDock`: высота, сворачивание):
  - слева — дерево: прогоны → вызванные документы → блоки, с состоянием и временем;
  - справа — журнал выбранного узла: вывод оболочки потоком, `console` кода, ошибки, аргументы (секреты скрыты);
  - кнопки: «Стоп» (узел и его поддерево), «Остановить всё», «Открыть документ» (на месте блока).
- Завершённые прогоны остаются в дереве (свёрнуты) до очистки или перезапуска приложения.

### Этап 4. Шаги «в чат» и «спросить ИИ»

- Основа — существующий `md template chat` (`blocks/tpl/run.ts`). Он уже отправляет заполненный текст в чат заметки, а упоминание агента в тексте запускает его ход. Расширять его, а не делать новый вид блока:
  - выбор комнаты — любая комната, доступная пользователю, а не только первая комната заметки;
  - ссылка на комнату — по её id, обновлять ссылку при переименовании комнаты не нужно.
- `ask=<агент>` — сообщение адресуется агенту, существующий механизм ходов агентов (`lib/agentTurns.ts`) запускает его ход. У агента есть MCP-инструменты приложения: читать и запускать заметки, писать логику.
- `wait` — дождаться ответа агента (с тайм-аутом) и опубликовать текст ответа значением. Без `wait` — отправить и идти дальше.

### Этап 5. Чтение файлов

- Блок `file`-чтения: путь (с подстановками, выбор файла кнопкой), формат по расширению (таблица форматов: txt, log → `{ text, lines }`; csv, xlsx → `rows`, лист `sheet=`; json → разобранное значение), `match=` для строк — как у оболочки.
- Чтение в main, предел размера, понятные ошибки «нет файла» / «нет доступа».
- Разбор xlsx и csv — переиспользовать существующие разборщики импорта таблиц.

### Этап 6. SSH

Отдельный документ устройства перед этапом. Направление:
- сохранённые сессии (хост, порт, пользователь, пароль или ключ; секреты — `safeStorage`), список — как подключения баз данных (`DbConnections`), блок ссылается по имени;
- блок оболочки с `ssh=<сессия>` выполняет команду на сервере с тем же договором о выводе;
- вкладка терминала по сохранённой сессии;
- библиотека — `ssh2` (зависимость main).

## Решения, принятые мной (проверить)

- Компонент вызова — блок `call`. Импорт в код — через существующий флаг `lib`, а не через новый.
- Возврат: `result`, если объявлен, иначе все значения прогона.
- Ручной запуск и cron продолжают писать сохранённые результаты; изолированы только вызовы из других документов.
- Рекурсия разрешена с пределом глубины 16.
- Аргументы — одно значение `args`, а не отдельные имена (нет столкновений с именами блоков).
- Значения в оболочку — и подстановкой, и переменными окружения `QA_<имя>`.
- Время жизни асинхронных вызовов — как у промисов JS (см. этап 2).
- Журнал — хвост в памяти, не полный вывод на диске.
- `skip` — при любом пакетном прогоне, включая проходы цикла; ручной запуск блока игнорирует флаг.
- ИИ вызывает документ новым MCP-инструментом, прогон изолирован.
- Cron не хранит аргументы; без умолчаний для обязательных — ошибка.
- Шаг «в чат» — расширение `template chat`, комната по id.
- Вопрос одобрения в фоне ждёт ответа 10 минут.

## Решения пользователя

- Запуск по кнопке или существующим cron-блоком; свой планировщик не нужен.
- Вызов документа — через компонент с выбором мышкой и поиском; параметры объявлены и нарисованы в вызываемом документе, как сигнатура функции.
- Вызов идёт в фоне; открытый документ показывает, что в нём выполняется сейчас; панель «Выполнение» с цепочкой вызовов, логами и остановкой.
- ИИ получает промпт и сам выбирает и запускает документ, проверяет что-то или пишет логику.
- Доверие к оболочке: свои скрипты — сразу; чужие и изменённые ИИ — после одобрения; настройка блока `ask=` (спрашивать каждый раз / разрешить всегда).
- Секреты маскируются по значению, как в CI.
- Порядок этапов: оболочка + галочки → документы-функции → панель → чат и ИИ → файлы → SSH.

## Оставлено исполнителю

- Точные имена видов блоков (`params`, `result`, `call`, `shell`, шаг чата, чтение файла), иконки, тексты команд «@».
- Где в окне футер и как устроен существующий нижний край экрана.
- Формат журнала прогона и его предел.
- Переиспользование кода разборщиков, ходов агента, переименования ссылок — найти и подключить, не копировать.
